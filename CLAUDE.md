# CLAUDE.md

## Общее правило

Перед внесением изменений в любой файл проверяй его актуальное
содержимое. Не полагайся на память: в файл могли внести правку
другие агенты или разработчики.

Если твои изменения меняют поведение, описанное в этом файле, —
обнови соответствующую секцию CLAUDE.md.

## Порядок работы

### Что читать перед задачей

- CLAUDE.md целиком — обязательно.
- `docs/requirements/step-NN-*.md` для текущего шага — обязательно.
- Записи `docs/ai-log/` прошлых шагов НЕ читай: текущее состояние проекта описывают
  код и CLAUDE.md, журнал — архив для человека. Исключение: задача прямо ссылается
  на конкретный файл журнала.
- README не читай, если задача не требует его правки.
- Файлы пакетов, которых задача не касается, не открывай. Нужен контекст по пакету —
  начни с его публичного API (`src/index.ts`), а не с обхода каталога.

### Как вести задачу

- Сначала прочитай задачу целиком. Если что-то противоречиво или допускает разные
  прочтения — назови это и спроси, прежде чем писать код: правка готового кода
  дороже уточнения. Если задача однозначна, вопросов не задавай и не пересказывай
  её обратно.
- Пиши только то, что требует задача. Кода «на вырост», обобщений «пригодится потом»
  и пакетов под будущую функциональность не заводи.
- Проверки прогоняй по завершении логического куска, а не после каждой правки файла.
- Если одна и та же проверка упала дважды подряд — остановись и опиши проблему
  и что пробовал. Перебор вариантов вслепую дороже вопроса.
- Не начинай следующую часть задачи, пока критерии готовности текущей не выполнены.

### Порядок проверок

Строго в этом порядке, каждый шаг — после того как предыдущий прошёл:

1. Форматирование (`prettier --write`) — один раз, когда код дописан.
   После этого шага код больше не форматируется: правки форматтера, приехавшие
   позже, сдвигают фрагменты мутаций и превращают их в `invalid`.
2. `npx lerna run typecheck --no-bail`
3. `npx lerna run lint --no-bail`
4. Тесты.
5. Наборы мутаций изменённых файлов.
6. Полный прогон мутаций — один раз, в конце задачи.

Возврат к шагу 1 после шага 5 означает повторение всей цепочки. Если после полного
прогона пришлось править код — прогони заново затронутые наборы, а не весь список.

Мутационный прогон ничего не делит с другими процессами: не запускай его параллельно
с тестами, сборкой или дев-сервером. `timeout` в результате — сначала перепроверь
набор в одиночку, и только если повторилось, разбирайся с самим тестом. Списывать
на нагрузку машины можно только после повторного прогона.

### Как прогонять проверки

- Перед первой проверкой в сессии включи нужный Node: `source "$HOME/.nvm/nvm.sh" && nvm use`
  (версия — в `.nvmrc`). Под Node 20 vitest падает на старте с `ERR_INVALID_ARG_VALUE` из
  `rolldown` (`The argument 'format' must be one of…`). Это не поломка тестов и не повод
  их чинить — это версия Node.
- Вывод проверок не тяни в контекст целиком: перенаправляй его в файл вне репозитория
  и смотри только итог и упавшее.
  - Тесты: `npm test > "$TMPDIR/test.log" 2>&1`, затем `tail -4 "$TMPDIR/test.log"` и
    `grep -E '^\s*FAIL' "$TMPDIR/test.log"`. Подробности упавшего теста доставай из лога
    точечно (`grep -A 20` по его имени), а не перечитывая весь вывод.
  - Мутации: `npm run test:mutation > "$TMPDIR/mutation.log" 2>&1`, затем
    `grep -E 'SURVIVED|INVALID|TIMEOUT|ERROR|не запускались|^Итого' "$TMPDIR/mutation.log"`.
    Прогон печатает строку на каждую мутацию, их больше двухсот; в контексте нужны только
    итог и не-`killed`.

## Структура пакетов (FSD)

- Слой FSD (`shared`, `entities`, `features`, `widgets`, `pages`) — это группа пакетов:
  каталог `packages/<слой>/`. Сам слой пакетом не является.
- Каждый пакет внутри слоя — одна функциональность: `packages/<слой>/<функциональность>`,
  имя `@<слой>/<функциональность>`, свой `package.json`, публичный API только через `exports`.
- Новая функциональность — новый пакет в своём слое, а не папка внутри существующего пакета.
- Слой пакета определяется тем, что он агрегирует, а не тем, откуда можно импортировать:
  - `entities` — сущность: её данные и её UI (карточки, представления одной сущности);
  - `features` — агрегация сущностей;
  - `widgets` — агрегация фич;
  - `pages` — страница из виджетов, фич и сущностей.
- UI, который работает с одной сущностью и не агрегирует фичи, — это не виджет: он живёт в
  пакете сущности. Пустой слой — нормально, пакет «на вырост» не заводится.
- Слой импортирует только нижележащие слои; пакет — только объявленное в своём `package.json`.
- Слой app — `apps/web`. `apps/mock-api` и `scripts/*` — вне слоёв.

## Модель компонента

- Состояние и логика компонента живут в хуке модели рядом с компонентом (`model/use<Имя>Model.ts`
  или хук с говорящим именем в `model/`); компонент рендерит то, что вернул хук.
- Правило применяется к новому коду и к коду, который и так меняется в задаче. Сплошной
  рефакторинг существующего кода под правило без отдельного задания не делается.
- Исключение — панорама и зум холста дерева (`TreeCanvas`): они сознательно идут мимо состояния
  React через rAF и ref ради критического пути рендеринга; переделка требует повторных замеров.

## Журнал решений: docs/ai-log/

Журнал хранит то, чего нет в диффе: почему принято решение, какие
альтернативы отброшены, где отступил от инструкции, что проверено.
Текущее состояние проекта описывают CLAUDE.md и код, а не журнал.

### Когда писать

- Одна запись на задачу: шаг, фичу или заметный рефакторинг. Не на каждую правку.
- Мелочи в журнал не записывай: опечатки, переименования, форматирование,
  обновление patch-версий. Для них достаточно сообщения коммита.
- Пиши в конце задачи, после проверок: в записи только то, что реально выполнено.

### Где и как называть

- Файл: `docs/ai-log/YYYY-MM-DD-<slug>.md`, дата — день начала задачи.
  Если в задаче есть номер шага: `YYYY-MM-DD-step-NN-<slug>.md`.
  Slug латиницей в kebab-case, 2–4 слова. Время в имени не нужно; при
  совпадении имён добавь суффикс `-2`.
- Общий файл журнала и файл-индекс не заводи: при параллельной работе
  в разных ветках они дают конфликты. Индекс — это `ls docs/ai-log/`.
- Если в задаче явно указано другое место для записи, следуй задаче.

### Правила

- Прошлые записи не переписывай. Если решение пересмотрено, опиши это
  в новой записи со ссылкой на старый файл. В старую допиши одну строку
  `> Пересмотрено: <имя нового файла>`.
- Фактическую ошибку в старой записи исправляй с пометкой
  `> Исправлено YYYY-MM-DD: …`, не стирая исходный текст молча.
- Результаты проверок пиши честно: непройденное — «не прошло»,
  с причиной и тем, что пробовал. Логи не копируй целиком, только ключевые строки.
- Не пиши секреты, токены, email и прочие персональные данные.
- Записи коммитятся: запись попадает в тот же коммит, что и изменения,
  которые она описывает.
- Секция «Авторство» обязательна: из неё собирается раздел README про AI.
  Заполняй её по ходу задачи, а не по памяти в конце. Правкой человека считается
  всё, что пришло не от агента: ТЗ и ревью, выбор в вопросах агенту, изменения
  файлов, замеченные между чтением и записью. Агент видит ручные правки только
  в файлах, которые читал, — так и пиши («агент не наблюдал»), а не «правок не было».

### Шаблон

```markdown
# Шаг NN — <название> (или просто <название>)

Дата: YYYY-MM-DD

<1–2 предложения: задача и итог.>

## Изменения

Кратко: какие пакеты или файлы затронуты. Без пересказа диффа.

## Решения

Решение → почему → какие альтернативы отброшены.

## Отступления от инструкции

Что сделано иначе и почему. Если отступлений нет — «Нет».

## Проверки

Команда → результат.

## Известные проблемы

Что осталось нерешённым. Если ничего — секцию опусти.

## Авторство

- Сгенерировано агентом: <файлы и решения>.
- Написано или переписано человеком: <файлы/фрагменты> или «Нет (агент не наблюдал)».
- Решения и указания человека: <ТЗ, выбор в вопросах, ревью>.
```

## Требования к следующим шагам: docs/requirements/

Требования, выявленные заранее (ревью, известные ограничения) и относящиеся
к конкретному будущему шагу, лежат в `docs/requirements/step-NN-<slug>.md`;
план сведения README — в `docs/requirements/readme.md`.

- Перед началом шага NN прочитай `docs/requirements/step-NN-*.md` целиком.
- Выполненный пункт отметь `[x]` и ссылкой на запись журнала; невыполненный —
  объясни в записи журнала, почему.
- Новое требование к будущему шагу записывай туда сразу, а не только в
  «Известные проблемы» журнала: журнал агент следующего шага не читает.
- При сведении README сверяйся с `docs/requirements/readme.md`.

## Мутационная проверка: scripts/mutation/

Наборы мутаций (`scripts/mutation/src/suites/`) описывают регрессии, которые тесты
обязаны ловить. Подробности — `scripts/mutation/README.md`.

- Изменил файл, для которого есть набор, — прогони его набор:
  `npm run test:mutation -- <набор>`. Полный прогон (`npm run test:mutation`) —
  один раз в конце задачи: он гоняет весь набор тестов по каждой мутации и стоит
  дорого, после каждой правки его запускать не надо. Вывод полного прогона фильтруй,
  как описано в «Как прогонять проверки».
- Фрагменты `from`/`to` пиши так, чтобы их не ломало переформатирование: минимальный
  различающий кусок кода без ведущих отступов и без строк, которые Prettier может
  перенести. Новую мутацию проверь на устойчивость — прогони `prettier --write` по
  её файлу и убедись, что она не стала `invalid`.
- `invalid` — код изменился: обнови `from`/`to`, сохранив смысл мутации. Если один и
  тот же фрагмент становится `invalid` повторно — переякори его, а не подправляй
  в очередной раз.
- `survived` — допиши тест; удалять мутацию, чтобы прогон позеленел, нельзя.
- Добавил тест на требование — добавь мутацию, которая это требование ломает, и
  убедись, что она `killed`.
- Таблицы мутаций в журнале и README бери из `npm run test:mutation -- <набор> --markdown`,
  не собирай вручную. Перечисляй только нужные наборы: `--markdown` без имён напечатает
  таблицу на все мутации проекта.
