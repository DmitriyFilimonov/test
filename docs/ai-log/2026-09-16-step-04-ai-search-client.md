# Шаг 04, часть 2 — AI-поиск на клиенте и ревью шага

Дата: 2026-09-16

Строка поиска принимает фразу: текстовый результат приходит сразу, разобранный фильтр ложится в
адрес, применяется к строкам таблицы на клиенте и виден плашкой с условиями. Часть 2 реализована
в другой сессии агента; в этой — ревью обеих частей: исправлены найденные дефекты, дописаны
dom-тесты и мутации части 2, документация приведена к отказу от словаря-заглушки.

## Решения

**Сначала пометить проходящие, затем достроить предков** → предков ищем по индексу всех строк,
а не по уже отфильтрованным: предок, сам не прошедший фильтр, иначе пропал бы вместе с веткой.
Проходящие — `matches: true`, достроенные предки — `matches: false`: таблица приглушает их так же,
как контекст текстового поиска. Порядок строк — исходный серверный.

**Дерево при структурном фильтре не приглушается** (трактовка) → приглушение следует за
`matches` из ответа сервера, их задаёт только `q`; структурный фильтр — инструмент таблицы.

**«Искать по тексту» — фраза из `lastParsedQuery`, одной навигацией** → к моменту клика `q` уже
очищен (см. отступления), и прежняя реализация брала пустой `params.q`: кнопка работала как
«Сбросить». Теперь фильтр снимается и фраза пишется в `q` одним `replace` (две навигации от
одного `searchParams` затёрли бы друг друга); та же фраза в `lastParsedQuery` подавляет повторный
разбор. После открытия по ссылке фразы нет — кнопка снимает фильтр с пустым полем.

**Подписи уровней: 1 — дивизионы, 2 — отделы, 3 — команды** → в данных уровень — глубина дерева
(дивизион → отдел → команда), а пояснение, плашка и инструкция модели называли уровень 1
«командами», 3 — «группами»; пример в промпте учил модель переводить «команды» в `levels: [1]`,
то есть в дивизионы. Исправлено в трёх подписях и в инструкции.

**Любой сбой модели → `null`, без проброса `AbortError`** → код пробрасывал ошибку с именем
`AbortError` из разбора в обработчик без `try`, то есть в 500. SDK `openai` при отмене бросает
`APIUserAbortError` с другим именем, так что на практике ветка не срабатывала, но это нарушение
главного свойства эндпоинта. Таймер снимается в `finally`, клиент модели создаётся внутри `try`.

**Кэш хранит только удачные разборы** → сбой сети или таймаут раньше навсегда (до перезапуска)
закреплял фразу за текстовым поиском. Одинаковость разбора одной фразы сохраняется: удачный
результат кэшируется, ссылка, которой поделились, модель не вызывает вовсе.

**Клиент модели — параметр `createSearchParseHandler`, ключ — `vi.stubEnv`** → тест пояснения
раньше полагался на кэш, заполненный предыдущим вызовом `parseQuery`, а сбой и отсутствие ключа
на уровне обработчика не проверялись. Маршрут в `app.ts` не изменился.

**Таймаут в тесте на fake timers** → тест ждал настоящие 30 с. Мок отвечает валидным фильтром
через `LLM_TIMEOUT_MS + 1000`: без отмены по таймауту тест падает сразу, а не зависает.

**Мутации части 1 переписаны** → «таймаут не срабатывает» была `invalid` (фрагмент с `15000`
при коде с `30000`), «сбой модели выходит как 500» меняла недостижимую ветку, «при пустом ключе
всё равно идёт вызов» отсутствовала; многострочные фрагменты с отступами заменены однострочными.

**Мутации части 2, неочевидные формулировки:**

- «разбор блокирует текстовый поиск» — таблица не монтируется, пока идёт разбор;
- «разбор запускается при открытии по ссылке» — подавление в `useSearchParse` не проверяется.
  Мутация «`hasParsedQuery` не смотрит на фильтр в адресе», по разбору кода, выжила бы (не
  прогонялась): при открытии ссылки с `q` и фильтром эффект очистки `q` отменяет таймер разбора
  раньше, чем тот сработает, — защита дублируется, тест её отдельно не различает;
- «структурный фильтр уходит в запрос и меняет ключ кэша» — фильтр подмешан в параметры
  `useOrgTree` таблицы.

## Отступления от инструкции

- **Словаря-заглушки нет** (решение человека): без `LLM_API_KEY` модель не вызывается и любой
  ответ — `mode: 'text'`. Тестов заглушки в коде к ревью уже не было; её раздел в README удалён.
- **Таймаут 30 с вместо 5 с** (сессия части 2, по заметкам): GLM 4.7 FlashX через прокси
  отвечает 10–15 с. Константа `LLM_TIMEOUT_MS` с комментарием.
- **При структурном фильтре `q` очищается, поле поиска заблокировано** (сессия части 2): иначе
  фраза оставалась бы в `q`, сервер не находил бы по ней совпадений и таблица была бы пустой до
  применения фильтра. Следствие — «нового запроса к `/api/org-tree` нет» выполняется, пока
  данные ключа с пустым `q` свежие (5 с): после долгого разбора уходит ревалидация этого ключа.
  Сам фильтр в запрос и ключ не попадает — это проверяет мутация.
- **Разбор ждёт ещё 250 мс после попадания текста в `q`** — `useSearchParse` дебаунсит `q`,
  который уже прошёл дебаунс поля. На фоне ответа модели 10–15 с не переделывалось.
- **Появление плашки и индикатора сдвигает таблицу вниз** — ТЗ требовало без сдвига. Оставлено:
  постоянное место над таблицей рассинхронизировало бы панели дерева и таблицы в split, а
  человек проверил работу руками и переделку работающего не просил.
- Полный прогон мутаций не выполнялся (указание человека) — только наборы изменённых файлов.

## Известные проблемы

- `q` из структурного ответа модели (`{ levels: [2], q: 'продаж' }`) клиент отбрасывает: в адрес
  попадают только числовые поля и уровни, а `q` очищается. Фраза вида «отделы продаж» покажет все
  отделы.
- По коду (тестом не проверялось): смена адреса во время разбора (режим, сортировка)
  перезапускает разбор — колбэк результата зависит от `searchParams`, эффект `useSearchParse`
  отменяет запрос и отправляет его заново.
- Ссылка с текстовым поиском (`?q=…`) при открытии отправляет `q` на разбор и может превратиться
  в структурный фильтр.
