Дата: 2026-09-15

экшены, селекторы) и хук `useQuerySubscription`. Один ключ и один фетчер на вызов

## Решения по API

```ts
const query = createQuery({
  name: 'orgTree', // reducerPath и префикс типов экшенов
  fetcher: (signal) => fetch(url, { signal }).then((r) => r.json()),
  parse: (raw) => schema.parse(raw), // TData выводится отсюда
  isEqual: (current, next) => deepEqual(current, next),
  staleTime: 5000, // необязателен
});
// query: { reducerPath, reducer, saga, actions, selectors }
combineSlices(query); // в @app/web
packageSagas.push(query.saga);
useQuerySubscription(query.actions); // в хуке пакета-сущности
```

- **`parse` — отдельная обязательная опция.** Фетчер отдаёт `unknown`, `parse` —
  единственная точка превращения `unknown` в `TData`. Воркер вызывает её через
  `call`: это эффект, его можно подменить, а исключение из `parse` даёт
  `status: 'error'` так же, как ошибка сети. Обязательность убирает молчаливое
  `as TData` у потребителя, а `TData` выводится из `parse`, так что явные дженерики
  не нужны (`name` при этом тоже выводится литералом).
- **`isEqual` обязателен.** Разумного значения по умолчанию нет: `Object.is` для
  свежего JSON всегда `false` (инвалидация на каждом ответе), глубокое сравнение
  дорого и зависит от предметной области.
- **`name` = `reducerPath`.** `createQuery` возвращает объект вида
  `{ reducerPath, reducer }`, поэтому регистрируется как `combineSlices(query)` —
  тот же механизм, что у слайсов (см. `2026-09-15-step-01-mock-api-store.md`).
  Селекторы принимают корневой стейт `{ [name]: QueryState<TData> }`.
- **Наружу только `subscribed`, `unsubscribed`, `requested`.** Экшены жизненного цикла
  (`fetchStarted/Succeeded/Failed/Cancelled`) диспатчит только воркер и в `actions`
  их нет; в devtools они видны.
- **`requested({ force })`, payload необязателен.** Без `force` уважает `staleTime`,
  с `force` — обходит. В обоих случаях не стартует, если задача уже идёт.
- **Редьюсер без Immer.** Сохранение ссылки выражено явно:
  `data: unchanged ? state.data : data`. С Immer пришлось бы следить, чтобы драфт не
  трогал вложенные поля, и типизировать `Draft<TData>` для обобщённого типа.
- **Успех сбрасывает `error`.** Задание говорит «обнови только fetchedAt и status»;
  `error` тоже сбрасывается, иначе после ретрая останется `status: 'success'`
  рядом со старой ошибкой. Ссылка на `data` при равенстве сохраняется, как требуется.
- **Отмена возвращает статус «как до запроса»:** `error` есть → `'error'`, есть данные
  → `'success'`, иначе `'idle'`. `fetchStarted` ошибку не стирает, поэтому её видно во
  время ретрая.
- **`fetchedAt` — время получения ответа**, а не старта запроса.
- **В `catch` нет проверки `cancelled()`.** Отменённая задача в redux-saga завершается
  через `generator.return()`: управление идёт сразу в `finally`, минуя `catch`.
  Поздний reject фетчера после `abort()` уже никто не слушает. Проверка в `catch`
  всегда давала бы `false`. Требование «отмена не становится ошибкой» закрыто
  тестом 5, где фетчер, как настоящий `fetch`, отклоняется с `AbortError` по abort.
  > Пересмотрено: `2026-09-15-step-01-review-fixes.md` — внешний `AbortError` в `catch` обрабатывается как отмена.
- **`(yield* call(parse, raw)) as TData`.** `SagaReturnType<(raw) => TData>` для
  обобщённого `TData` TypeScript не раскрывает (TS2322); `parse` синхронный, поэтому
  приведение корректно.
- **Хук зависит от `react-redux`.** Страницам `react-redux` запрещён линтером, поэтому
  они вызывают не этот хук, а публичный хук пакета-сущности, который его оборачивает.

## Почему рефкаунт устроен так

- **Счётчик и ссылка на задачу — локальные переменные вотчера, не Redux-стейт.**
  Это координация эффектов, а не данные: от них ничего не рендерится. В сторе они
  потребовали бы отдельных экшенов, а решение «прочитать счётчик → форкнуть» стало
  бы двумя шагами с окном между ними.
- **Один последовательный цикл `take` на три экшена.** Вотчер обрабатывает экшены по
  одному, а `fork`/`cancel`/`select` в нём не блокируют. Поэтому каждое решение
  атомарно относительно счётчика и задачи без блокировок: две подписки в одном тике —
  вторая уже видит живую задачу (тест 2).
- **Свежесть только в саге через `select`.** Хук не читает `fetchedAt`: N компонентов,
  смонтированных одновременно, не принимают N независимых решений по своим
  замыканиям, а решение опирается на стор в момент обработки экшена.
- **Живость задачи — `task.isRunning()`,** ссылка не обнуляется в `finally`. Воркеру не
  нужно сообщать вотчеру о завершении, значит нет второго канала координации.
- **Не более одного запроса в полёте.** И подписка, и `requested({ force })` не
  стартуют при живой задаче. Поэтому невозможна гонка, в которой старый ответ
  перезаписывает более новый, и не нужен механизм версионирования ответов.
- **Отмена ровно при переходе в 0.** Запрос, который никому не нужен, прерывается
  через `AbortController`; пока есть хотя бы один подписчик, запрос живёт (тест 6).
  `requested` на счётчик не влияет.
- **Счётчик не уходит ниже нуля** (лишний `unsubscribed` зажимается к 0).

Следствие, которое стоит знать: **React StrictMode** в dev монтирует эффекты как
«подписка → отписка → подписка» синхронно. По этим правилам первый запрос
стартует, отменяется (abort) и сразу стартует второй: в dev в сети будет один
отменённый запрос. Поведение зафиксировано отдельным тестом. Избежать можно,
откладывая `cancel` на тик после перехода в 0, но это расходится с «стало 0 и задача
жива → cancel» из задания, поэтому не сделано.

> Пересмотрено: `2026-09-15-step-01-strict-mode-off.md` — приложение работает без StrictMode.

## Известные проблемы

- `useQuerySubscription` не покрыт тестом: нужен DOM-рендер (jsdom +
  @testing-library/react — новые зависимости). Хук — один `useEffect` с двумя
  dispatch; поведение подписок покрыто на уровне саги.
- Счётчик живёт в экземпляре саги. Если корневая сага упадёт и перезапустится,
  счётчик обнулится при смонтированных компонентах — связано с нерешённой
  изоляцией саг из `2026-09-15-step-01-mock-api-store.md`.
  > Пересмотрено: `2026-09-15-step-01-review-fixes.md` — изоляция соседних саг решена `supervise`; обнуление счётчика при перезапуске осталось.
- npm: первый `npm i -D … -w @shared/query` в только что созданный workspace лишь
  создал симлинк и не записал зависимости (так же было с `express` в mock-api);
  повторная команда сработала.
