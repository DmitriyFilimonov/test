# Шаг 01 — численность и эффективность подразделения в карточке

Дата: 2026-09-15

Карточка родителя показывала `headcount` из JSON (собственных сотрудников узла) как
«Численность», хотя в подразделении людей больше. Теперь карточка узла с дочерними
показывает собственные и общие значения численности и эффективности рядом, у листа — только
«Численность» и «Эффективность». Общая эффективность взвешена так, что каждый человек учтён
один раз.

## Изменения

- `@entities/org-tree` — селектор `selectSubtreeAggregates`; у узлов видимого дерева поле
  `subtree` (итоги по всему подразделению, включая скрытых потомков); тесты агрегата и
  селекторов, пример из обсуждения.
- `@widgets/org-tree` — `lib/nodeMetrics.ts`: `getNodeMetrics` (собственные и общие значения,
  округление, диапазоны цвета) и `getMetricRows` (какие строки показывать); `OrgNode` рисует
  строки списком `<dl>`, без `title`; тесты `nodeMetrics.test.ts`.
- `@shared/theme` — `performanceNone`, узел 256×136 (было 216×84): четыре подписанные строки
  не помещались.
- `scripts/mutation` — набор `widgets-node-metrics` (6), мутация в `entities-selectors`.
- `README.md`, `docs/requirements/step-02-table.md`.

## Решения

- **Смысл полей.** Выбран вариант, подтверждённый пользователем на примере: `headcount` в JSON —
  собственные сотрудники подразделения. Общая численность = собственные + общая у дочерних
  (2 + 2 + 2 = 6); общая эффективность = Σ(собственная эффективность × собственные сотрудники)
  / общая численность ((2·80 + 2·60 + 2·40) / 6 = 60). Контракт API, мок и `touch` (меняет
  ровно один узел) не менялись; инвариант «родитель = собственные + сумма дочерних» соблюдается
  по построению, проверять в схеме нечего.
- **Отвергнуто:** `headcount` в JSON как готовый итог (избыточно, изменение команды меняет всю
  цепочку предков, веса по итогам дают двойной счёт) и люди только в листьях (не описывает
  руководителей подразделений).
- **Четыре подписанных поля вместо одного числа и подсказки.** Первая версия правки показывала
  одно число «Численность» с итогом и собственные значения в `title`; пользователь отметил, что
  так непонятно, откуда берутся числа, а `title` — слабый приём. Итоговая версия — пары
  «собственные / общие» для численности и эффективности, у каждой эффективности свой индикатор
  (цвет + число).
- **Лист — два поля** (указание пользователя): у листа общие значения всегда равны собственным.
  Лист определяется по данным (`childCount === 0`), а не по уровню. Размер узла одинаковый для
  всех: отдел без команд — тоже лист, а размер должен быть одинаковым в пределах уровня.
- **Собственная эффективность при 0 собственных сотрудников — «—»**, как и общая при 0 людей:
  средневзвешенное не определено.
- **Общая эффективность округляется, цвет — по округлённому значению**: пользователь видит 90 —
  цвет «top», а не «high» от 89.5.
- **Цвета — статические правила** по `data-performance` (общая) и `data-own-performance`
  (собственная): по 6 правил, не от числа.
- **Чистые функции `getNodeMetrics`/`getMetricRows`** — чтобы правило отображения было покрыто
  тестами и мутациями без DOM-рендера.

## Отступления от инструкции

- Размер узла в теме увеличен до 256×136.

## Проверки

- Команды: typecheck 12/12, lint 12/12, `npx vitest run` — 11 файлов, 106 тестов;
  `npm run test:mutation` — 46/46 killed; `npm run build -w @app/web` — успешно; prettier — чисто.
- Мутации новых правил: общая численность = собственной, общая эффективность = собственной,
  «—» при 0 собственных, цвет по неокруглённому значению, лист с четырьмя строками, «нет
  данных» без выделения, видимое дерево без итогов — все убиты.
- Браузер (production, «Развернуть всё», 53 карточки): все четыре значения каждой карточки
  совпадают с посчитанными по ответу API; у листьев 2 строки («Численность», «Эффективность»),
  у узлов с дочерними 4; атрибутов `title` в карточках 0. Пример: «Дивизион коммерческих
  продуктов» — собственных 4, общая численность 78, собственная эффективность 53, общая 72.
- После `POST /api/dev/touch` листа и ревалидации общая численность изменилась на ту же дельту у
  команды, её отдела и дивизиона (−2: 7 → 5, 32 → 30, 97 → 95); все значения совпадают с API.
  (В проверке `touch` вызывался до попадания в лист, промежуточные вызовы меняли другие узлы.)
- Скриншоты (2x): подписи и числа помещаются в карточку.
- Сдвиг макета за цикл «загрузка → данные → ревалидация» — 0 записей; число CSS-правил
  styled-components после трёх ревалидаций постоянно (47).
- Раскрытие одного узла (dev, временный счётчик, откачен) — перерисованы 4 `OrgNode` из 22.
- Профиль (CPU 4x): после первой версии четырёх полей «Развернуть всё» дало задачу 53 мс;
  после сокращения листьев до двух полей — 41 мс, длинных задач нет. Панорама — макс. 10 мс,
  82 кадра на 82 движения; зум — макс. 6 мс, 33 кадра на 61 событие; принудительного layout нет.
  Первая загрузка — одна задача ~117 мс (без изменений, см. `2026-09-15-step-01-tree-render.md`).

## Известные проблемы

- Бюджет в карточке не показывается; итоги по бюджету уже считаются (`subtree.budget`).
- Правило отображения живёт в `@widgets/org-tree`; для таблицы на шаге 02 его нужно вынести
  ниже, а не копировать (записано в `docs/requirements/step-02-table.md`).
