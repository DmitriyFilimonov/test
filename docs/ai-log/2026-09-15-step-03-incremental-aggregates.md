# Шаг 03, часть 2 — Инкрементальный пересчёт агрегатов

> Пересмотрено: 2026-09-16-step-03-live-apply.md

Дата: 2026-09-15

Реализация инкрементального пересчёта агрегатов: при обновлении узла пересчитываются только он и его предки, а не всё дерево.

## Изменения

- `packages/entities/org-tree/src/model/aggregate.ts` — добавлены `AggregateIndex` (Map с накопленными суммами через Symbol), `applyAggregatePatch()` для инкрементального пересчёта. Для добавления/удаления — полный пересчёт.
- `packages/entities/org-tree/src/model/aggregate.patch.test.ts` — 12 тестов: эквивалентность с полным расчётом (200 случайных деревьев, на каждом — серия из 1–5 патчей по 1–3 узла), локальность (ссылки сохраняются), счётчик (3 записи для листа на глубине 3), 100 патчей одного узла, удаление/добавление, патч корня, несуществующий узел.
- `packages/entities/org-tree/src/model/selectors.ts` — `selectSubtreeAggregates` теперь возвращает `AggregateIndex`, добавлен `toSubtreeAggregate` для преобразования в публичный тип `SubtreeAggregate`.
- `packages/entities/org-tree/src/index.ts` — экспортируются `applyAggregatePatch`, `AggregateIndex`, `AggregateChanges`.
- `scripts/mutation/src/suites/entities-aggregate-patch.ts` — новый набор с 6 мутациями: локальность нарушена, цепочка предков обрывается, накопленные суммы не обновляются, удаление не вычитает поддерево, эффективность накапливается дробями, патч без изменений не возвращается.
- `scripts/mutation/src/suites/entities-org-tree.ts` — обновлены `from`/`to` в `entitiesAggregateSuite` под новую структуру кода (Symbol вместо явного поля).
- `README.md` — добавлен раздел «Инкрементальный пересчёт агрегатов» с объяснением счётчика затронутых узлов; таблицы мутаций перегенерированы целиком (`npm run test:mutation -- --markdown`, 206 мутаций против прежних 164) — в них не хватало и наборов части 1 (`shared-live-*`, `mock-api-stream-*`).
- `docs/requirements/step-03-live-apply.md` — требования к части 3: где применять патч, сигнатура, разрыв `seq`, целочисленность бюджета, перенос поддерева.

## Решения

**Накопленные суммы через Symbol** → `weighted` нужен для разностного пересчёта, но не должен быть в публичном API `SubtreeAggregate`: Symbol-ключ не подберёшь по имени и не сериализуешь случайно. Поле заводится неперечислимым (`Object.defineProperty`), поэтому не попадает и в `toEqual` — существующие тесты сравнивают записи индекса с литералом из трёх полей и остались без правок по смыслу.

**Полный пересчёт для добавления/удаления** → структурные изменения ломают индексы детей и цепочки предков. Инкрементальный пересчёт потребовал бы перестройки всех индексов и сложнее в отладке. На 53 узлах разница в миллисекундах не заметна.

**Индекс в Map, а не в объекте** → id могут быть любыми строками, включая `__proto__`. Map безопаснее и быстрее для частых обновлений.

**Ранний выход при пустом патче убран** → оптимизация, которую не ловят мутации. Следующая проверка `patched.size === 0` возвращает исходный индекс в любом случае.

**Применение патча — в редьюсере, не в селекторе** → инкрементальный пересчёт по определению зависит от предыдущего индекса, а `createSelector` видит только текущие данные: «предыдущее» пришлось бы держать скрытым изменяемым состоянием внутри селектора. Это сломалось бы на многоключевом кеше (`@shared/query` хранит записи по ключу параметров: у каждого ключа свои данные и свой индекс) и на втором сторе в тестах. Поэтому индекс должен жить рядом с данными в сторе: полный расчёт — на ответ GET, `applyAggregatePatch` — на событие patch, селектор только читает готовый индекс. Существующий тест «агрегаты пересчитываются только при изменении данных» это выдерживает: мемоизация по ссылке на данные остаётся, а полный расчёт на каждый патч не запускается, потому что патч вообще не создаёт новый массив данных для полного прохода.

**Дрейфа нет** → численность и эффективность объявлены целыми в схеме узла (`z.number().int()`), их сложение и вычитание точны; общая эффективность — деление двух целых сумм, а не накопление дробей. Тест на 100 патчей проверяет отсутствие накопления ошибки.

Оговорка, которой требовало ТЗ («если это не так — скажи»): бюджет в схеме объявлен как `z.number().min(0)`, без `.int()`. Мок-API отдаёт бюджеты целыми (кратными 10 000), поэтому фактического дрейфа нет, но контракт дробный бюджет допускает — на нём разностный пересчёт бюджета накапливал бы погрешность. Схему не ужесточал: это изменение контракта, а не задача этого шага. Записано в `docs/requirements/step-03-live-apply.md`.

## Отступления от инструкции

**Сигнатура `applyAggregatePatch(index, previousNodes, currentNodes, changes)` вместо `applyAggregatePatch(index, nodes, changes)`.** Разностный пересчёт требует прежних значений изменённых узлов, а индекс хранит итоги по поддереву, не собственные значения узла; вытаскивать «было» вычитанием детских итогов — лишняя арифметика и лишний источник ошибок. Прежние данные у вызывающей стороны есть всегда: патч применяется к тому массиву, что лежит в сторе.

**Применение патча выбрано (редьюсер), но не подключено.** В этом шаге патчи до данных не доходят: часть 1 явно оставила поток на состоянии соединения и `lastSeq`, часть 2 запретила трогать транспорт и UI. Поэтому `applyAggregatePatch` пока вызывается только из тестов; требования к подключению записаны в `docs/requirements/step-03-live-apply.md`, чтобы агент следующей части их прочитал.

Правки `from`/`to` в наборе `entities-aggregate` (обе — под переписанный `aggregateSubtrees`, смысл мутации прежний):

- «среднее не взвешено по headcount»: было `weighted: node.performance * node.headcount,`, стало `let weighted = node.performance * node.headcount;`. Взвешенная сумма была полем промежуточного объекта `totals`, теперь это локальная переменная обхода. Мутация по-прежнему убирает умножение на численность.
- «нулевой headcount даёт деление на ноль вместо null»: было `performance: total.headcount > 0 ? … : null,`, стало `entry.performance = entry.headcount > 0 ? … : null;`. Тот же тернарник переехал из литерала объекта в присваивание записи. Мутация по-прежнему убирает ветку с `null`.

## Известные проблемы

- Смена родителя узла (перенос поддерева) разностным путём не обрабатывается: в контракте патча её нет (есть только `nodes`/`added`/`removed`), а `applyAggregatePatch` берёт цепочку предков из текущих данных. Если перенос появится в контракте, его нужно вести по ветке полного пересчёта, как добавление и удаление.
