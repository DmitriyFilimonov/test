# Модель данных

Узел оргструктуры, дерево из узлов, расчёт итогов по поддереву и контракт потока изменений.
Как эти данные проходят через приложение — в [architecture.md](architecture.md).

## Узел

`GET /api/org-tree?q=&sort=&dir=` возвращает плоский массив узлов. Схема — `orgNodeSchema` в
[`schema.ts`](../packages/entities/org-tree/src/model/schema.ts), строгая: лишнее поле или
неверный тип — ошибка всего ответа.

| Поле          | Тип               | Смысл                                                                                    |
| ------------- | ----------------- | ---------------------------------------------------------------------------------------- |
| `id`          | непустая строка   | идентификатор узла                                                                       |
| `name`        | непустая строка   | название подразделения                                                                   |
| `parentId`    | строка или `null` | родитель; `null` — корень                                                                |
| `headcount`   | целое ≥ 0         | **собственные** сотрудники: закреплённые непосредственно за подразделением, без дочерних |
| `budget`      | число ≥ 0, руб.   | собственный годовой бюджет, без дочерних                                                 |
| `performance` | целое 0–100       | эффективность собственных сотрудников                                                    |
| `updatedAt`   | ISO 8601, UTC     | время последнего изменения узла; проверяется и календарь (30 февраля не пройдёт)         |
| `matches`     | boolean           | совпало ли собственное `name` с `q` без учёта регистра; при пустом `q` — `true`          |
| `order`       | целое ≥ 0         | позиция узла в серверной сортировке, сквозная по всем узлам                              |

Первые семь полей — данные узла, они хранятся на сервере. `matches` и `order` сервер считает под
параметры запроса: разные `q`, `sort`, `dir` дают разные значения при одних и тех же узлах.
Поэтому они приходят в ответе GET, но не в патчах потока.

```json
[
  {
    "id": "org-54cb82",
    "name": "Дивизион финансов и операций",
    "parentId": null,
    "headcount": 7,
    "budget": 34810000,
    "performance": 41,
    "updatedAt": "2026-07-13T15:57:00.000Z",
    "matches": true,
    "order": 4
  },
  {
    "id": "org-1413b2",
    "name": "Отдел логистики",
    "parentId": "org-54cb82",
    "headcount": 2,
    "budget": 13590000,
    "performance": 31,
    "updatedAt": "2026-07-31T23:58:00.000Z",
    "matches": true,
    "order": 44
  }
]
```

## Дерево

Иерархия задана только ссылками `parentId`: вложенности в ответе нет, порядок массива ничего не
значит. Это лес — корней может быть сколько угодно; раскладка оборачивает их в виртуальный
корень.

**Целостность** проверяется вместе со схемой (`orgTreeResponseSchema`), любое нарушение — ошибка
всего ответа:

- `id` уникальны;
- `parentId` указывает на существующий узел;
- циклов нет (проверка за O(n): каждый путь к корню проходится один раз);
- `order` — перестановка `0..n-1`.

**Уровень** — глубина узла от корня: дивизион — 1, отдел — 2, команда — 3. В данных его нет,
клиент считает его обходом индекса детей (`selectNodeLevels`).

**Индексы**, которые клиент строит из массива (мемоизированные селекторы в
[`selectors.ts`](../packages/entities/org-tree/src/model/selectors.ts)):

| Индекс                    | Вид                    | Для чего                                       |
| ------------------------- | ---------------------- | ---------------------------------------------- |
| `selectChildrenIndex`     | `parentId → дети`      | видимое дерево, «Развернуть всё»               |
| `selectParentIndex`       | `id → parentId`        | раскрытие предков выбранного узла              |
| `selectNodeLevels`        | `id → уровень`         | колонка «Уровень», фильтр AI-поиска по уровням |
| `selectSubtreeAggregates` | `id → итоги поддерева` | карточки, таблица, фильтр AI-поиска            |

**Данные мока** — 53 узла: 5 дивизионов → отделы → команды, генерируются из зашитого сида и не
меняются между перезапусками, пока их не изменят дев-ручки или генерация патчей. Одна команда —
без сотрудников, чтобы был виден случай «эффективность не определена».

**Равенство ответов** (`isSameOrgTree`): тот же набор `id` и у каждого узла тот же `updatedAt`.
Равный ответ не меняет ссылку на данные в сторе. `matches` и `order` не сравниваются: они
зависят от параметров, а параметры входят в ключ кеша.

## Алгоритм агрегации

Код — [`aggregate.ts`](../packages/entities/org-tree/src/model/aggregate.ts).

### Определения

Для узла `v` и его поддерева `T(v)` (сам узел и все потомки):

```
totalHeadcount(v)   = Σ headcount(u),               u ∈ T(v)
totalBudget(v)      = Σ budget(u),                  u ∈ T(v)
weighted(v)         = Σ performance(u) · headcount(u), u ∈ T(v)
totalPerformance(v) = weighted(v) / totalHeadcount(v),  если totalHeadcount(v) > 0
                    = null,                             иначе
```

Каждый человек учитывается ровно один раз: `headcount` — собственные сотрудники, поэтому итог
родителя — его собственные плюс итоги детей, без двойного счёта. Эффективность взвешена по
людям: команда из 2 человек влияет на итог меньше, чем команда из 20. Подразделение без людей
не влияет на среднее; если людей нет во всём поддереве, эффективность — `null` (в UI «—»).

Пример: у двух дочерних по 2 сотрудника с эффективностью 80 и 60, у родителя свои 2 с
эффективностью 40:

```
totalHeadcount   = 2 + 2 + 2 = 6
weighted         = 2·80 + 2·60 + 2·40 = 360
totalPerformance = 360 / 6 = 60
```

UI показывает эффективность округлённой (`Math.round`). Дробное значение хранится в индексе:
округлять промежуточные итоги нельзя — ошибка накопится вверх по дереву.

### Полный расчёт — `aggregateSubtrees(nodes)`

O(n) по времени и памяти, без рекурсии (цепочка из десятков тысяч узлов не переполняет стек):

1. Один проход: индекс `parentId → дети` и список корней.
2. Прямой обход в глубину стеком от корней — порядок, в котором родитель стоит раньше потомков.
3. Проход по этому порядку в обратную сторону — дети обработаны раньше родителя. Для узла:
   собственные значения плюс уже посчитанные записи детей.

Результат — `Map<id, { headcount, budget, performance }>`. Сумма `weighted` хранится в записи
скрытым полем (символ, не перечисляется): она нужна для инкрементального пересчёта, а
потребителям не видна. Узлы, недостижимые от корня (цикл, битый `parentId`), в результат не
попадают — валидная схема таких данных не пропускает.

### Инкрементальный пересчёт — `applyAggregatePatch`

Патч метрик меняет итоги только самого узла и его предков. Вместо полного прохода:

1. Для каждого изменённого узла — разности `Δheadcount`, `Δbudget`,
   `Δweighted = performance'·headcount' − performance·headcount`. Нулевые разности пропускаются.
2. Подъём по `parentId` до корня: к записи каждого предка прибавляются разности,
   `performance` пересчитывается делением новых сумм. Предок, общий для нескольких изменённых
   узлов, берётся из уже пересчитанных записей — разности складываются.
3. Новый `Map` копирует прежний и заменяет только пересчитанные записи. Записи остальных узлов —
   те же ссылки.

Стоимость — O(глубина) на изменённый узел: патч листа на глубине 3 трогает ровно 3 записи.
Добавление и удаление узла меняют структуру (индекс детей, цепочки предков) — для них полный
пересчёт.

Дрейфа нет: `headcount` и `performance` целые по схеме, бюджет мок отдаёт целым, а
`totalPerformance` каждый раз получается делением двух целых сумм, а не накоплением дробей.
Оговорка: схема не требует целого `budget`; на дробных бюджетах разностный пересчёт накапливал
бы погрешность с плавающей точкой.

### Где хранится индекс

Индекс — производное значение, в Redux его нет. `getAggregateIndex(nodes)` держит его в `WeakMap`
по ссылке на массив узлов: один расчёт на данные, общий для дерева и таблицы, и память
освобождается вместе с данными. После патча сага кладёт в `WeakMap` индекс, посчитанный
инкрементально, **до** записи новых данных в стор — селектор находит готовый индекс и полного
расчёта не запускает.

Мок-сервер считает те же итоги своим кодом для сортировки по `totalHeadcount`, `totalBudget`,
`totalPerformance` ([`org-tree-query.ts`](../apps/mock-api/src/org-tree-query.ts)): он вне слоёв и
пакеты приложения не импортирует. Совпадение определений проверено тестами каждой стороны.

### Тесты

- [`aggregate.test.ts`](../packages/entities/org-tree/src/model/aggregate.test.ts) — пример выше,
  лист, суммы по поддереву, взвешенное среднее, узел без людей, `null` при нулевом итоге,
  независимость от порядка массива, цикл.
- [`aggregate.patch.test.ts`](../packages/entities/org-tree/src/model/aggregate.patch.test.ts) —
  совпадение с полным расчётом (один лист, несколько узлов, 200 случайных деревьев со случайными
  сериями патчей), локальность (прочие записи — те же ссылки, счётчик затронутых записей), 100
  патчей одного узла без накопления ошибки, полный пересчёт при добавлении и удалении, пустой
  патч и патч без реальных изменений.
- Мутации `entities-aggregate` и `entities-aggregate-patch` в `scripts/mutation` ломают взвешивание,
  `null` при нулевой численности, локальность, цепочку предков и накопленные суммы — и проверяют,
  что эти тесты падают.

## Контракт потока патчей

> **Транспорт — Server-Sent Events, а не WebSocket.** Поток односторонний: сервер сообщает об
> изменениях, клиент ничего не отправляет. Почему не WebSocket и не опрос —
> [ADR-003](adr/003-sse-live-transport.md). Содержимое событий от транспорта не зависит: те же
> `hello` и `patch` без изменений можно передавать сообщениями WebSocket.

Схемы клиента — [`live.ts`](../packages/entities/org-tree/src/model/live.ts), сервер —
[`org-tree-stream.ts`](../apps/mock-api/src/org-tree-stream.ts).

### Соединение

`GET /api/org-tree/stream`

```
HTTP/1.1 200 OK
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

Кадры — стандартный формат SSE: `event:` с именем события, `data:` с JSON в одну строку, пустая
строка в конце кадра.

| Кадр           | Когда                      | Данные                                                                                    |
| -------------- | -------------------------- | ----------------------------------------------------------------------------------------- |
| `event: hello` | сразу после подключения    | `{ "seq": <текущий seq сервера> }`                                                        |
| `event: patch` | на каждое изменение данных | патч, см. ниже                                                                            |
| `: ping`       | каждые 20 с                | комментарий SSE, клиенту не доставляется; не даёт прокси закрыть простаивающее соединение |

```
event: hello
data: {"seq":186}

event: patch
data: {"seq":187,"nodes":[{"id":"org-b8e684","headcount":5,"performance":90,"updatedAt":"2026-09-16T13:37:58.484Z"}],"removed":[],"added":[]}

: ping
```

### `seq`

- Номер изменения данных от старта сервера. Растёт на 1 на каждое изменение — даже когда
  подписчиков нет: это позиция сервера, а не номер отправленного сообщения.
- `hello` сообщает текущую позицию, первый патч после него будет `seq + 1`.
- После перезапуска сервера отсчёт начинается с 0 — для клиента это `hello` с другим номером.

### Патч

```ts
type OrgTreePatch = {
  seq: number; // целое ≥ 0
  nodes: OrgNodeChange[]; // изменённые узлы
  removed: string[]; // id удалённых узлов
  added: Omit<OrgNode, 'matches' | 'order'>[]; // добавленные узлы
};

type OrgNodeChange = {
  id: string;
  headcount?: number; // новое значение, если изменилось
  budget?: number;
  performance?: number;
  updatedAt: string; // при любом изменении
};
```

- Все объекты строгие (`z.strictObject`): лишнее поле — нарушение контракта. Ограничения
  значений — те же, что у узла в ответе GET.
- В `nodes` — **новые значения**, а не приращения: повтор изменения безвреден.
- `name` и `parentId` существующего узла патчем не меняются. Структура меняется только через
  `added` и `removed`.
- Сервер удаляет только листья: иначе у детей остался бы `parentId` на несуществующий узел.
- `added` — узел как в ответе GET, но без `matches` и `order`: они зависят от параметров
  запроса.

### Обработка на клиенте

| Ситуация                                      | Действие                                                                    |
| --------------------------------------------- | --------------------------------------------------------------------------- |
| неизвестное событие, не JSON, нарушение схемы | событие пропускается и логируется, соединение остаётся                      |
| `seq` ≤ последнего учтённого                  | повтор — игнорируется                                                       |
| `seq` = последний + 1                         | патч применяется к данным текущего ключа кеша без запроса                   |
| `seq` > последний + 1                         | патчи потеряны — полный перезапрос текущего ключа                           |
| `hello` после переподключения с другим `seq`  | пока соединения не было, сервер ушёл вперёд или перезапустился — перезапрос |
| у текущего ключа ещё нет своих данных         | патч не применяется: данные придут ответом на запрос                        |

Применение патча (`applyOrgTreePatch`):

- **изменённый узел** получает новые значения и `updatedAt`, остаётся на прежней позиции `order`
  (строки не прыгают под курсором, даже если новая сумма сортировала бы их иначе);
- **удалённый узел** исчезает, `order` следующих сдвигается — порядок остаётся перестановкой
  `0..n-1`;
- **добавленный узел** встаёт последним по `order`; `matches` — `true` при пустом `q`, иначе
  `false` до ответа сервера (совпадение с `q` клиент не вычисляет); уже известный `id` не
  добавляется повторно;
- **итоги** пересчитываются инкрементально (выше);
- **подсветка** — для узлов, у которых изменилось показанное значение (собственная и общая
  численность, собственная и общая эффективность после округления, общий бюджет), в стор
  записывается `seq` патча;
- **другие ключи кеша** (другие `q`, `sort`, `dir`) не патчатся, а помечаются протухшими: их
  `matches` и `order` считает сервер. При возврате к ключу данные перезапрашиваются
  ([ADR-004](adr/004-live-patches-into-query-cache.md)).

Переподключение: пауза — случайная величина от 0 до `min(30 с, 1 с · 2^n)`, после 10 неудач
подряд попытки прекращаются; возврат вкладки на экран — попытка сразу.

### Известное ограничение

Ответ `GET /api/org-tree` не содержит `seq`. Патчи между сборкой ответа и первым `hello` не
видны как пропуск, а ответ, собранный раньше патча, перезаписывает его значения до следующего
патча. Снимается номером `seq` в ответе GET.
