# ADR-005: Инкрементальный пересчёт итогов по цепочке предков

- Статус: принято
- Дата: 2026-09-15
- Источник: `docs/ai-log/2026-09-15-step-01-headcount-aggregates.md`,
  `2026-09-15-step-03-incremental-aggregates.md`, `2026-09-16-step-03-live-apply.md`

## Контекст

API отдаёт собственные значения узла: сотрудники, бюджет, эффективность. Карточки дерева,
таблица и фильтр AI-поиска показывают итоги по поддереву: общую численность, бюджет и
эффективность, взвешенную по людям. С шага 03 данные меняются патчами каждые несколько секунд.

ТЗ шага 03 (часть 2) потребовало пересчитывать при обновлении узла только его и предков и
проверять это счётчиком затронутых узлов, а не таймером. На 53 узлах полный проход по абсолютным
цифрам быстрее — требование про архитектуру, а не про миллисекунды.

## Решение

- **Индекс хранит накопленные суммы**, а не только показываемые значения: `headcount`, `budget`
  и `weighted = Σ performance · headcount` (скрытым полем записи). Средняя эффективность — деление
  двух сумм.
- **`applyAggregatePatch`** для изменённых метрик считает разности и поднимается по `parentId` до
  корня, прибавляя их к записям предков. Остальные записи — те же ссылки.
- **Структурные изменения** (добавление, удаление) — полный пересчёт `aggregateSubtrees` за O(n).
- **Индекс вне Redux:** `WeakMap` по ссылке на массив узлов. Сага кладёт инкрементальный индекс
  в `WeakMap` до записи данных в стор — селектор находит готовый и полного расчёта не запускает.

Алгоритм подробно — [data-model.md](../data-model.md#алгоритм-агрегации).

## Альтернативы

- **Полный пересчёт на каждый патч.** Проще и на текущем объёме быстрее, но не выполняет
  требование и растёт линейно с размером дерева.
- **Хранить в индексе только среднюю эффективность.** Из среднего нельзя вычесть вклад узла без
  суммы весов; пересчёт через дроби накапливал бы погрешность.
- **Итоги в Redux.** Производные данные рядом с исходными — два источника правды и лишний экшен
  на каждое изменение; `WeakMap` освобождается вместе с данными.
- **Итоги от сервера.** Контракт отдаёт собственные значения; патч одного узла пришлось бы
  дополнять итогами всех предков.

## Последствия

- Патч листа на глубине 3 трогает ровно 3 записи — проверяется тестом со счётчиком.
- Эквивалентность полному расчёту проверяется на 200 случайных деревьях со случайными сериями
  патчей и на 100 патчах одного узла.
- Дрейфа нет, пока значения целые: `headcount` и `performance` целые по схеме, бюджет мок отдаёт
  целым. Схема целый бюджет не требует — на дробных бюджетах разностный пересчёт копил бы
  погрешность.
- Итоги считаются и на сервере (для сортировки) отдельным кодом с теми же определениями:
  мок-сервер вне слоёв и пакеты приложения не импортирует.
