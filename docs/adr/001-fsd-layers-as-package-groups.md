# ADR-001: Слой FSD — группа пакетов, пакет — функциональность

- Статус: принято
- Дата: 2026-09-15
- Источник: `docs/ai-log/2026-09-15-step-01-scaffold.md`,
  `2026-09-15-step-01-feedback-roots-fsd.md`, `2026-09-15-step-01-widget-to-entity.md`

## Контекст

Задание: монорепозиторий на npm workspaces и Lerna, код по слоям Feature-Sliced Design
(`shared`, `entities`, `features`, `widgets`, `pages`, `app`), абсолютные импорты, границы слоёв
закреплены линтером. Нужно было решить, что считать пакетом, как пакеты резолвят друг друга и
как определять слой нового кода.

Первая формулировка в README — «слои FSD — отдельные пакеты» — допускала один пакет на слой, в
котором функциональности лежат папками. Дерево сначала попало в `@widgets/org-tree`: оно
рисует холст и карточки и потому казалось «виджетом».

## Решение

- **Слой — каталог `packages/<слой>/`, пакет внутри — одна функциональность**
  `@<слой>/<функциональность>` со своим `package.json`. Новая функциональность — новый пакет, а не
  папка в существующем (указание автора).
- **Слой определяется тем, что пакет агрегирует**, а не тем, откуда его можно импортировать:
  сущность — данные и UI одной сущности, фича — агрегация сущностей, виджет — агрегация фич.
  Дерево работает с одной сущностью, поэтому его UI — в `@entities/org-tree`; слои `features` и
  `widgets` пусты (указание автора).
- **Пакеты не собираются.** `exports: { ".": "./src/index.ts" }`, резолв — через симлинки
  workspaces, `paths` и алиасов нет. Зависимость на пакет — версия `"*"` в `package.json`.
- **Границы — ESLint:** `no-restricted-imports` по скоупу `@<слой>/*` (слой не импортирует
  вышележащие и `@app/*`), `import/no-extraneous-dependencies` с `includeInternal` (пакет
  импортирует только объявленное), `import/no-relative-packages` (нет обхода через `../../`),
  `import/no-unresolved` (глубокий импорт мимо `exports` не резолвится).

## Альтернативы

- **Один пакет на слой, функциональности — папками.** Такое прочтение допускала первая
  формулировка README; правило автора «пакет — функциональность» его исключает: границы между
  функциональностями внутри слоя не были бы видны ни зависимостям, ни линтеру.
- **Раскладка по ответственности:** холст — в `shared`, карточка — в сущность, композиция — в
  виджете. Предлагал агент, автор отклонил: слой по агрегации даёт однозначный ответ, куда класть
  новый код.
- **`eslint-plugin-boundaries`.** Классифицирует элементы по путям разрезолвленного импорта, а у
  workspace-симлинков это зависит от обработки realpath резолвером — лишняя точка отказа, лишняя
  зависимость и свой DSL. Слой однозначно виден по скоупу импорта, regex достаточно.
- **Сборка пакетов (`tsc`) или `paths` в tsconfig.** Шаг сборки на каждый пакет и расхождение
  резолва между TypeScript, Vite и Node. `exports` + симлинки резолвятся одинаково везде.

## Последствия

- Добавить функциональность — завести пакет с `package.json`, `tsconfig.json`, скриптами `lint` и
  `typecheck`; Lerna подхватывает его автоматически (сейчас 13 проектов).
- Внутренности пакета закрыты: наружу только то, что экспортирует `src/index.ts`.
- Страницам запрещены `react-redux`, `redux-saga`, `@reduxjs/toolkit` — со стором они работают
  через хуки сущности. Пакетам запрещён `import.meta.env`.
- Исходники пакетов лежат вне `node_modules`, поэтому Vite нужен `resolve.dedupe` для `react`,
  `react-dom`, `styled-components`, `react-redux` — иначе две копии контекста.
- Координация дерева и таблицы — на странице (`useOrgDashboardModel`), а не в виджете: фич для
  агрегации нет.
