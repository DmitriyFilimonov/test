# ADR-002: Многоключевой кеш stale-while-revalidate на redux-saga

- Статус: принято
- Дата: 2026-09-15
- Источник: `docs/ai-log/2026-09-15-step-01-shared-query.md`,
  `2026-09-15-step-01-review-fixes.md`, `2026-09-15-step-02-multikey-cache.md`

## Контекст

Стек — React, Redux Toolkit и redux-saga — задан заданием. Слой загрузки данных —
`@shared/query`, stale-while-revalidate на redux-saga со stale time 5 секунд, — тоже часть задания. На шаге 02
у запроса появились параметры (`q`, `sort`, `dir`): дерево и таблица подписываются на одни и те
же данные, пользователь быстро меняет фильтр, возвращается к прежним параметрам.

Требования: не больше одного запроса на одни параметры, отмена ненужных запросов, отсутствие
мигания пустотой при смене параметров, отсутствие перерисовок при ревалидации равными данными.

## Решение

`createQuery({ name, fetcher, parse, isEqual, getKey, staleTime, gcTime, debounceMs })` возвращает
`{ reducerPath, reducer, saga, actions, selectors, getKey }`.

- **Запись кеша на ключ** `getKey(params)` — стабильная сериализация параметров (порядок полей
  не важен, `undefined` опускается).
- **Решения принимает одна сага-вотчер.** Счётчики подписчиков и задачи запросов — в локальных
  `Map` вотчера, а не в сторе; `subscribed`, `unsubscribed`, `requested` обрабатываются в одном
  последовательном цикле `take`. «Прочитать счётчик → форкнуть запрос» — атомарно, по каждому
  ключу не больше одного запроса, разные ключи грузятся параллельно.
- **Отмена.** Уход последнего подписчика ключа отменяет задачу, `AbortController` прерывает
  `fetch`; отмена возвращает статус «как до запроса» и ошибкой не становится.
- **Debounce** — эффект `debounce` redux-saga на окно: по окончании окна запрос получает каждый
  ключ, подписанный за окно и всё ещё с подписчиками.
- **Данные прежнего ключа.** Пока у нового ключа нет данных, селектор отдаёт данные последнего
  успешного ключа с `isPlaceholder: true`.
- **Вытеснение.** Запись без подписчиков удаляется через `gcTime` (5 мин) задачей с `delay`;
  новая подписка задачу отменяет.
- **`parse` и `isEqual` обязательны.** `parse` — единственная точка превращения `unknown` в
  данные, его исключение даёт `status: 'error'`. Если `isEqual(текущие, новые)`, ссылка на `data`
  сохраняется, меняется только `fetchedAt`.
- **Изменение данных без запроса** (шаг 03): `patched(params, updater)` и
  `invalidated(predicate)` — см. [ADR-004](004-live-patches-into-query-cache.md).

## Альтернативы

- **RTK Query, TanStack Query.** В журнале не рассматривались: слой на redux-saga задан заданием.
- **Счётчики подписчиков в сторе.** Решение «запустить запрос» читало бы стор и диспатчило бы
  отдельным шагом; между ними успевает пройти другой экшен. Счётчики — координация эффектов, а не
  состояние для UI.
- **Буквальный debounce (`takeLatest` с задержкой).** Одновременные подписки на разные ключи
  (дерево и таблица с разными параметрами) теряли бы все, кроме последней.
- **Сравнение ответов по максимальному `updatedAt`.** Пропускает удаление узла — воспроизведено
  на моке; взято сравнение набора `id → updatedAt` (выбор автора).
- **Проверка `cancelled()` в `catch`.** Отменённая задача завершается через `iterator.return()` и
  в `catch` не попадает; при этом внешний `AbortError` из фетчера обрабатывается как отмена, иначе
  статус залипает в `loading`.

## Последствия

- Компоненты только объявляют подписку (`useQuerySubscription`); когда ходить в сеть, решает сага.
- Равный ответ не перерисовывает дерево и таблицу; индекс агрегатов по ссылке на данные тоже
  не пересчитывается.
- Счётчики живут в саге: если супервизор перезапустит упавшую сагу, они обнулятся.
- Trailing debounce откладывает и первую загрузку, поэтому у оргдерева `debounceMs` не задан, а
  паузу ввода фильтра держит `useTableModel`.
- Отмена без отложенного окна: быстрый уход и возврат на страницу отменяет запрос и отправляет
  заново. Снимается откладыванием отмены на N мс.
