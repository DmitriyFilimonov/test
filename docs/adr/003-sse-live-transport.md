# ADR-003: Server-Sent Events для обновлений в реальном времени

- Статус: принято
- Дата: 2026-09-15
- Источник: `docs/ai-log/2026-09-15-step-03-live-transport.md`,
  `2026-09-16-step-03-live-apply.md`, `2026-09-16-step-04-docker.md`

## Контекст

Шаг 03: изменения оргструктуры на сервере должны доходить до открытых вкладок без перезагрузки,
а клиент — показывать состояние соединения. Поток односторонний: сервер сообщает об изменениях,
клиенту отправлять по этому каналу нечего. В dev запросы идут через прокси Vite, в Docker —
через nginx.

## Решение

- **Транспорт — SSE:** `GET /api/org-tree/stream`, `Content-Type: text/event-stream`. Именованные
  события `hello` (текущий `seq`) и `patch` (изменение с `seq`), комментарий `: ping` раз в 20 с.
  Контракт — [data-model.md](../data-model.md#контракт-потока-патчей).
- **Повторы делает клиент, а не браузер.** На первой ошибке `EventSource` закрывается, сага
  `@shared/live` ждёт паузу full jitter — случайную от 0 до `min(30 с, 1 с · 2^n)` — и открывает
  новый. После 10 неудач подряд — `failed` и кнопка «Подключиться». Возврат вкладки на экран —
  попытка сразу.
- **Соединение одно на вкладку**, открывается первым подписчиком и закрывается последним;
  состояние (`status`, `attempt`, `retryAt`, `lastSeq`) — в сторе для индикатора.
- **Пропуски видны по `seq`,** а не по `Last-Event-ID`: клиент при пропуске перезапрашивает данные
  целиком ([ADR-004](004-live-patches-into-query-cache.md)), серверу не нужно хранить историю
  патчей.

## Альтернативы

- **WebSocket.** Двусторонний обмен не нужен. Потребовались бы отдельная обработка upgrade на
  сервере и в прокси, свой протокол сообщений поверх сокета, свой heartbeat и переподключение —
  то, что SSE даёт форматом и `EventSource`.
- **Опрос (polling).** Запросы при отсутствии изменений; задержка реакции равна интервалу опроса.
- **Встроенный повтор `EventSource`.** Нельзя управлять ни паузой, ни числом попыток; все вкладки
  после сбоя сервера переподключались бы синхронно.

## Последствия

- Работает поверх обычного HTTP и прокси, но прокси не должен буферизовать и сжимать поток. В
  nginx для `location = /api/org-tree/stream` — `proxy_buffering off`, `gzip off`,
  `proxy_read_timeout 1h`; сервер дополнительно шлёт `X-Accel-Buffering: no` и
  `Cache-Control: no-transform`. Проверено: с буферизацией и сжатием события не доходили.
- Поток занимает одно HTTP-соединение на вкладку; при HTTP/1.1 это одно из шести соединений
  браузера к origin.
- Клиент не может ничего отправить по потоку: разбор поисковой фразы — отдельный `POST`.
- Содержимое событий от транспорта не зависит: переход на WebSocket меняет `@shared/live` и сервер,
  но не контракт `hello`/`patch` и не применение патчей.
